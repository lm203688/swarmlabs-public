# 「综合虚拟实验室」方向可行性评估

> 日期：2026-09-21 ｜ 评估对象：用户提出的「综合虚拟实验室 + 验证即服务」方向
> 判据来源：`docs/goal_realignment_2026-09-09.md` §1 单一判据；`docs/action-vs-core-goal-audit-20260919.md`
> 事实来源：`engine/domains.py`、`engine/real_datasets.py`、`scripts/real_validation.py`、`frontend_fixed/reports/wet_lab_anchors.json`、`docs/market-position-2026-09-21.md`

## 0. 结论先行

| 问题 | 裁决 |
|---|---|
| 这个方向可行吗？ | **条件可行**——且比「从零新建一个综合实验室」可行性**高得多**，因为仓库里已有约 70% 骨架 |
| 唯一硬条件 | **真实数据只能作「事后作证」，绝不能作「前置输入」**。一旦倒置，产品从「替代真实实验」退化成「编排真实实验」，既违反 09-09 判据、也失去护城河 |
| 「数据量不重要」对不对？ | **对一半**：accumulated 语料规模确实不是护城河（本文支持停掉数量竞赛）；但替代它的不是「每次抓真实数据」，而是**方法论通用性 + 验证可靠性 + 锚定覆盖** |
| 最大缺口 | **外部提交 / 编排入口不存在**（没有「客户发来一个实验」的 intake→scope→job→verdict 管道） |
| 最大风险 | **抓错的真实数据 → 自信地给出错误裁决**，这会一击摧毁「可信验证层」定位 |

## 1. 把你说的模型精确化（先消歧，再评估）

你的原话可归纳成一条服务流水线：

```
客户提交「一个需要验证的实验」
   → 智能体做数据收集（该实验方向的核心数据）
   → 完成实验组织（虚拟实验搭建 + 进程控制）
   → 多维度验证
   → 输出：该项事务的验证裁决 / 可归档报告
（分专业；项目自身的数据量不是关键）
```

这句话里**有一个必须钉死的歧义**，它决定整个方向是成立还是崩塌：

| 读法 | 含义 | 后果 |
|---|---|---|
| **读法 A（成立）** | 虚拟实验**独立成立**（不依赖真实数据），真实数据只是**事后**拿来作证 / 做 parity 锚定 | ✅ 产品=「替代真实实验的验证层」，offline 可跑，护城河在方法论+门禁 |
| **读法 B（崩塌）** | 虚拟实验**需要**真实数据才能给出结论（真实数据是前置输入） | ❌ 产品退化成「真实实验的编排器」，被 SciencePro / OpenResearch 正面碾压，且离开网络/真实实验就不能用 |

**09-09 单一判据直接判定**：只有读法 A 通过。读法 B 会让「虚拟实验在无真实实验 / 无网络 / 无设备下更可替代」这句话失效。

→ 本评估**全文按读法 A 展开**，并把「真实数据事后作证」写成架构约束（见 §4）。

这几乎就是你描述的商业模式的技术原型，只是目前挂在「引擎验证」场景，没挂到「客户工单」上。

## 3. 逐维度可行性打分

| 维度 | 可行性 | 理由 / 差距 |
|---|---|---|
| 方法论通用化 | **高** | 内核本就与专业解耦（GP/算子/多保真都是通用数学）；换专业=换数据与场景定义，非换引擎 |
| 虚拟实验搭建 | **中高** | 已有 82 场景与作者化范式；但新专业要写物理模型/ODEs/基准，是「每专业一次性建设」 |
| 多维度验证 | **高** | 门禁族已成型且 fail-closed；这是最强的一块，也是别人不愿做的一块 |
| 多专业扩展 | **中** | taxonomy 已存在；瓶颈不是「能不能」，是「每个新专业要花几天还是几周」 |
| 每实验真实数据作证 | **中** | 原型在（real_validation）；瓶颈是「为这一具体实验找对参照数据」目前靠人工，自动抓取有垃圾进风险 |
| 对外编排 / 工单 | **低（缺）** | 完全没有 intake/scope/job 管道；这是把它做成「服务」必须补的一层 |
| 数据量不重要 | **成立** | 见 §4 辨析 |

## 4. 核心辨析：「数据量不重要」对不对？

这是你整个设想里**最需要说清的一句**，因为它同时含着正确与危险两半。

### 正确的半句（我同意，且与既有战略一致）

- **accumulated 语料规模不是护城河**。对方（SciencePro/平台级）是 2.7 亿级论文；我方 15.7 万实体，差 ~1700×，数量竞赛必输。`docs/market-position-2026-09-21.md` 已把「实体库扩容」降为副产品。→ 你说「数据量不重要」与既有结论**同向**。
- 「每实验方向/专业都不同」意味着**数据不可跨实验复用**，所以堆量确实无意义。

### 危险的半句（必须纠正）

- 「因为每次安排真实数据验证」→ 这句把**一个依赖换成了另一个依赖**：从「大语料依赖」换成「每实验真实数据依赖」。后者不是零成本，它要付：
  1. **每专业参照数据的获取 + 归一化 + 单位对齐**（垃圾进 → 自信地错）；
  2. **谁来保证「这次抓到的真实数据是对的」**——这本身又需要一层验证，否则可信层的地基是自己没验证的数据。
- 所以准确表述应是：**数据「体量」不重要，但「每实验的锚定质量」极其重要**。替代体量的护城河是：**方法论通用性 + 验证可靠性 + 锚定覆盖**，不是「我们会抓数据」。

### 架构裁决（写死成约束）

```
虚拟实验先独立成立（不喂真实数据也要出结论 + 区间）
        ↓  通过 fail-closed 门禁
真实数据事后作证（parity / 锚定 chip）—— 只增信，不改判
        ↓
输出裁决：PROCEED / BLOCK / 无法评估（fail-closed 诚实说"做不到"）
```

这条顺序**不可倒置**。倒置即读法 B，即出局。

## 5. 建议的「综合虚拟实验室」流水线架构

```
[客户] 发来一个实验
   │  ①Intake：方向/专业/目标量/可提供的少量真实点
   ▼
[Scope] 落成 scenario spec（专业标签 + 输入输出 + 适用边界草案）
   │  ②专业路由：domains.py taxonomy → 已有内核 or 需新接
   ▼
[Build] 虚拟实验搭建（方法论文法：GP/算子/多保真 + 主动学习选点）
   │  ③进程控制：autonomous_loop / world_model / instrument_simulator
   ▼
[Verify] 多维度验证（fail-closed）
   │  R² + 区间覆盖 + 校准 + 锐度 + 反伪 + 文献锚定 + 双向 parity
   ▼
[Corroborate] 事后真实数据作证（少量真实点 → 诚实误差棒）
   │  ⚠ 只增信，不改判；抓不到就诚实标 UNANCHORED
   ▼
[Deliver] 裁决 + 可归档 10 章 V&V 报告（篡改可捕获的 vv_package）
```

## 6. 商业模式可行性：「验证即服务」

**判定：可行，但有三个前提、三个诚实风险。**

**三个前提**
1. **有 intake/scope 层**：能把「客户一句需求」转成可执行的 scenario spec（目前完全缺，是最大工程量）。
2. **专业接入边际成本可摊薄**：首个专业是慢的（写模型+基准）；之后靠 `domains.py` 的「发表基准做 gold+UQ」机制复用。**这条决定它是护城河还是人力跑步机**。
3. **交付物可独立复验**：`vv_package`（篡改一字节即 exit 2）已具备，客户/审方能离线核对——这是「验证服务」的信任地基。

**三个诚实风险**
1. **垃圾进风险**：抓错的参照数据会产出「自信的错误裁决」，重创信任定位。
2. **责任边界**：给出 BLOCK/PROCEED 就要为错杀/漏杀负责；fail-closed 门禁是护栏，但需写清「我们只对『可验证性』负责，不对科学发现负责」。
3. **规模≠即时**：「每个专业都不一样」意味着**新专业不是开箱即用**，营销上不能承诺「任意实验秒出」，否则兑现不了。

## 7. 必须建的四块（带优先级）

| # | 要建的东西 | 为什么 | 优先级 |
|---|---|---|---|
| 1 | **Intake / Scope / Job 编排层** | 没有它，这只是个库不是一个「服务」 | **P0** |
| 2 | **专业接入脚手架**（把「发表基准→gold→UQ」流程化，让它可复用而非每次手写） | 决定多专业是护城河还是人力跑步机 | **P0** |
| 3 | **锚定数据层硬化**：为「这一具体实验」找参照 → 自动候选 + 人工确认 + 单位/归一化校验（防垃圾进） | 「真实数据作证」的可信前提 | **P1** |
| 4 | **对外交付契约**：scenario spec 格式 + 裁决字段 + 复验说明（客户端可离线核对） | 服务可被第三方验收 | **P1** |

## 8. 与既有战略的关系（防止又跑偏）

- ✅ **同向**：它把「让虚拟实验在更多真实场景站得住」从「82 个固定场景」推广到「任意来单实验」，正是 09-09 判据的**泛化**，不是背离。
- ✅ **坐实**：「数据量不重要」= 正式停掉实体库数量竞赛（与 market-position §6「不做清单」一致）。
- ⚠️ **红线**：不得把「真实数据」变成前置输入；不得把「组织实验」做成「组织真实实验物流」（那是 CRO 公司，另一个物种）。
- ⚠️ **红线**：仍不做融资外联 / 竞品营销物料——本方向是纯技术打磨，资本是结果。

## 9. 需要你拍板的一个分叉

「每次实验的真实数据作证」有两条技术路线，架构不同，需你选：

| 路线 | 客户提供少量真实点 | 我方可信度最高（数据来源明确） | 适用：客户已有实验数据，要"少数据→全预测+误差棒" |
|---|---|---|---|
| **B** | 我方自动抓取文献锚定 | 覆盖广但垃圾进风险高 | 适用：客户只有一句需求，要"凭文献基准验证" |
| **A+B** | 两者都有：优先用客户数据，无则文献锚定 | 最稳，但要建两层 | **建议** |

**我的建议**：以 **A 为主（客户端少量真实点）**，因为它最符合 `real_validation.py` 的现成范式、数据来源最干净、责任边界最清晰；文献锚定作为**备选增信**（且必须人工确认，不能全自动抓）。
